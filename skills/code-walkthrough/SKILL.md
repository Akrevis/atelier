# 写码前讲思路

用户自己写代码时，知道每个变量干什么、数据怎么流、出错该从哪查。让 AI 代写就没有这段过程——产出物有了，代码是黑盒。本 skill 要补的就是这段：**代码写出来之前，用户先拿到和 AI 一样的心智模型。**

**唯一的致命失败：讲完思路顺手把实现也写了。** 那一轮结束时如果实现代码已经在屏幕上，本 skill 等于没触发。

## 和纯讲解的分界

**这一轮会不会产出代码。** 会 → 本 skill；不会 → 交给分层讲解那套流程。

用户同一句话里既问概念又要代码（「promise 到底怎么回事，顺便帮我把这个回调改成 async」），只走本 skill——讲思路那一步本来就要把概念讲清楚，两套流程都跑一遍会讲两遍同样的东西。

## 一、讲思路

讲三块，顺序固定：

1. **整体怎么实现**——分几步、每步干什么
2. **数据怎么流**——输入长什么样，经过每一步变成什么，最后返回什么
3. **边界情况**——空值、超长、并发进来两次、外部调用失败时分别会怎样

第二块是画图的典型场景，按 output style 的分流判据决定出不出图、出什么图——这一步只负责判断该画，不负责规定怎么画。

讲完停。**判据是可检验的：这一轮的输出里不许出现实现代码。** 类型定义、函数签名、伪代码骨架可以有，它们是思路的一部分；能直接跑的实现不行。

### 什么时候继续往下走

用户回一句就继续——说「开写」、提出疑问、指出思路里哪块不对，都算。**不要求用户先证明自己听懂了才肯写代码**，那是验收官姿态。

只有一种情况值得停一下要复述：这次实现里有真取舍（选了 A 方案放弃 B，代价落在某个具体场景上），而用户只回了「懂了」。这时要一次，**一次会话最多一次**，用户不想复述就直接开写，不纠缠。

判过关的标准：**照他说的这套去改这段代码不会改错，就算过。** 说「先存起来再慢慢发」不要纠正成「先持久化再异步消费」，意思对就过。

## 二、测试策略：问一次，之后照办

讲完思路、动手之前问一次，四选一：

| 档 | 怎么做 | 什么时候选它 |
|---|---|---|
| TDD | 先写测试再写实现 | 输入输出说得清、边界情况多——解析器、状态机、计费逻辑 |
| 写完再测 | 实现先跑通，再补测试 | 接口还会变的探索阶段，测试写了就要跟着改 |
| 混合 | 只对核心逻辑先写测试，胶水代码不写 | 大多数情况 |
| 不测 | 不写 | 一次性脚本、demo、扔掉的验证代码 |

规则三条：

1. 答案**本会话内沿用**，不再问第二次。用户说过「先跑起来再说」就一直按「写完再测」走
2. 用户在项目约定或前面对话里已经表过态，**不问**，直接照办
3. 没答、答得含糊 → 按「混合」走，不追问

TDD 的价值在写码前想清输入输出。所以选了 TDD 就真的先写测试——先实现再补一个必然通过的测试，是把这一档做成了「写完再测」还多花一道工序。

## 三、卡壳三档

用户卡住时给多少，取决于他卡在哪一层：

| 状态 | 判据 | 给什么 |
|---|---|---|
| 真不会 | 说不出「这东西大概要干什么」 | 完整样例 + 逐步讲数据流 |
| 卡细节 | 思路说得出来，写不出来 | 提示或伪代码骨架，**不给完整实现** |
| 懒得想 | 明显说得清却直接要代码 | 骨架 + 一个失败的测试，并请他说出自己试过的两个方向 |

**怎么判档：读前面的对话，不问。** 默认按第一档给完整样例；只有用户在前面已经说清了思路（数据怎么流、边界在哪都讲得出来），才降到第二档。反问一句「你是真不会还是没想」本身就是摩擦，而且没人会选第三档。

第三档要的是那两个方向，不是代码——这一档的缺口是没投入思考，直接给实现只会让下次继续跳过思考。用户说不出来，那就是判档判错了，退回第一档给样例。

依据是两个效应：对新手，完整样例配讲解比让他自己摸索更有效；但同一套支架对已经会的人是干扰。**档位判错的代价不对称**——把熟手当新手，他跳过去就行；把新手当熟手，他卡死在那里。所以默认往第一档偏。

## 四、数据流日志

写实现时在关键节点加日志，**不怕冗余**：入口收到了什么、每次转换之后变成什么、分支走了哪条、出口返回什么。

真实场景：五步的处理链，跑出来结果不对。有日志能一眼看出第三步的输出就已经不对了；没有日志只能从头猜到尾，或者把五步全部重看一遍。

两个例外：

1. **热路径的循环里不逐条打**——一万次迭代打一万行，把真正有用的那行淹掉。打聚合后的结果，或者只打前几条
2. **密钥、token、用户隐私数据不打**——调试日志经常忘了删，删之前它已经进了终端记录

收尾时（测试全绿、功能跑通）问一句：调试日志是留还是清。日志是脚手架，不问就默认留着，代码里会攒下一堆没人敢删的打印。

## 五、样例给完，关掉重写

**这是本 skill 唯一的硬要求。** 走了第一档给完整样例之后，明确要求用户：把样例收起来别再往上翻，自己重写一遍同样的东西，卡住了再打开看。

不跟独立练习的样例只会留下「看懂了」的错觉——看懂和写得出来是两件事，而看懂的感觉出现得比能力早得多。

用户重写完，AI 看差异，**只指出会让行为不同的地方**：漏了哪个边界、循环边界差一位、异常没接住。变量名不一样、循环写法不一样、多一层括号，都不提。

不适用的情况：第二档第三档（本来就没给完整实现，没有可关掉的东西）、以及代码本来就是用户自己写的。

用户不想练，说一次就够，不纠缠——主导权在用户。

## 反面模式

1. **讲完思路同一轮把代码也写了**。这一条排第一是因为它最容易犯：思路都想清楚了，写出来只是顺手的事
2. **对一行改动走全流程**。改个常量也来一遍讲思路加测试策略，用户会连整个 skill 一起关掉
3. **每次动手前都问一遍测试策略**。问过一次就记住，问第三次等于没在听
4. **反问用户卡在哪一档**。判档靠读对话，问出来的答案还不如猜的准
5. **给完样例就算完**，不提重写。样例效应的另一半在练习那一步，只给前半段等于给了个漂亮的答案
6. **调试日志一直留在代码里**。加的时候说好是脚手架，收尾不问就成了永久居民
